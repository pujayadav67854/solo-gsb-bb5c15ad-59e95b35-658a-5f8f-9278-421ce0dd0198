# 食品加工换线过敏原追踪

本地运行的食品加工过敏原溯源应用：登记**原料过敏原、设备、按时间排序的加工与已核实清洗事件**，
自动推导每个产出批次的过敏原集合、设备残留与来源路径，支持按"当时结果"登记放行；
更正任何早期事件后，受影响的后续批次、设备残留与放行状态都会重算。

- 后端：Node.js + Express
- 数据库：SQLite（[better-sqlite3](https://github.com/WiseLibs/better-sqlite3)），数据文件保存在本地卷/目录
- 前端：零构建的浏览器原生页面（HTML/CSS/JS）

---

## 一键启动（Docker Compose，推荐）

需要 Docker 与 Docker Compose 插件。在项目根目录执行：

```bash
docker compose up --build -d
```

首次启动会自动完成：

1. 安装全部依赖（`better-sqlite3` 优先使用预编译二进制，镜像内置编译工具链作为回退）；
2. 初始化 SQLite 数据库与全部表结构；
3. 对**空数据库**写入一批演示数据（可用环境变量 `SEED=0` 关闭，只建空表）；
4. 启动 Web 服务。

然后用浏览器打开：

> **http://localhost:3000**

停止：

```bash
docker compose down          # 保留数据
docker compose down -v       # 连同数据卷一起删除（回到空环境）
```

查看日志 / 重新构建：

```bash
docker compose logs -f
docker compose up --build    # 代码变更后重新构建启动
```

### 不使用容器（本地 Node.js）

要求 Node.js ≥ 18（开发使用 20）：

```bash
npm install
npm start
```

打开 http://localhost:3000 。数据默认写入项目下的 `data/allergen.db`。

运行核心逻辑测试：

```bash
npm test
```

## 页面与端口

| 内容 | 地址 |
| --- | --- |
| 应用页面 | http://localhost:3000 |
| 全量状态 API（含推导结果） | http://localhost:3000/api/state |

页面包含四个标签页：

1. **批次推导与放行**：按加工时间展示每个批次的过敏原并集、逐条来源路径，以及放行历史；
2. **事件录入（加工 / 清洗）**：新增或更正事件；加工事件可添加多个原料/前序批次输入；
3. **原料**：维护原料与其过敏原（提供常见致敏物类别快速选择，也可自由输入）；
4. **设备与残留**：维护设备，查看各设备截至最晚事件时的残留过敏原及其来源路径。

顶栏始终汇总当前仍带过敏原残留的设备。

## 配置

通过环境变量配置（容器内见 `docker-compose.yml`）：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `PORT` | `3000` | HTTP 监听端口。Compose 映射的宿主机端口也用同名变量控制：`PORT=8080 docker compose up --build -d` |
| `HOST` | `0.0.0.0` | 监听地址 |
| `DATA_DIR` | 容器 `/data`；本地 `./data` | SQLite 数据库所在目录 |
| `DB_PATH` | `${DATA_DIR}/allergen.db` | 数据库文件完整路径 |
| `SEED` | `1` | 空库启动时是否写入演示数据，`0` 表示只建空表 |

也可以复制 `.env.example` 为 `.env` 后修改 `PORT` / `SEED`，Compose 会自动读取。

数据持久化：Compose 使用命名卷 `allergen-data`；本地运行直接写入 `./data`。

## 业务规则与推导模型

### 过敏原推导

- 加工事件产出一个批次，**产出过敏原 = 全部输入过敏原 ∪ 设备当前残留过敏原**；
  - 原料输入：取原料登记的过敏原；
  - 前序批次输入：递归取该批次的推导结果（因此跨批次传递完整来源路径）；
  - 设备输入（隐式）：加工时该设备上未被清洗清除的残留过敏原会一并带入。
- 加工完成后，该设备残留更新为本批次的产出过敏原及其来源路径（产出集合本身已是输入∪旧残留）。
- **已核实清洗**（填写核实人）才会清空对应设备残留；**未核实清洗后残留原样保留**，换产仍会携带。
- 同一台设备同一时刻只允许一个事件；不同设备同一时刻允许并行。
- 每条过敏原都保留从"当前批次 ← 前序批次/设备残留 ← …… ← 原料"的完整来源路径，页面可展开查看。

### 放行

- 在批次卡片上点击「登记放行」，系统以**当时**的推导结果固化过敏原快照（集合、放行人、时间）。
- 任何更正/删除触发重算后：
  - 若批次仍在、但最新过敏原集合与放行快照**不同**，该放行自动置为 **失效**，并标注原因（旧集合 → 新集合）；
  - 若产出批次的加工事件已被删除，放行同样失效，原因注明"放行依据不存在"；
- 已经失效的放行不会被覆盖，永久保留留痕；可在结果更正后登记新的放行。

### 更正与整次提交拒绝

新增、更正、删除都在单个 SQLite 事务中完成：先写入临时状态，再对**全量事件**统一校验与重算，
任一规则不满足则整次回滚，数据保持原样，页面顶部会列出全部拒绝原因。以下情况会被拒绝：

- **引用未来批次**：前序批次的加工时间必须早于当前事件（同时刻也不允许）；
- **形成循环**：批次引用图中出现环（如 A→B→A），会给出环路链路；
- **同一设备事件时间冲突**：同设备两条事件（含加工与清洗）占用同一时刻；
- 其它：加工缺少输入、引用不存在的原料/批次、批次号重复、已核实清洗缺少核实人、删除仍被引用的原料等。

更正早期事件后，系统对全部事件按时间重新排序推导，因此**所有受影响的后续批次、设备残留、放行状态都会级联更新**。

## HTTP API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 全量数据 + 推导结果（批次、残留、放行） |
| POST/PUT/DELETE | `/api/materials[/:id]` | 原料增改删 |
| POST/DELETE | `/api/equipment[/:id]` | 设备增删（删除级联删除其事件） |
| POST/PUT/DELETE | `/api/events[/:id]` | 加工/清洗事件增改删（请求体含 `inputs`） |
| POST | `/api/releases` | 按当前推导结果登记批次放行 |

校验失败统一返回 `400`，响应体形如 `{ "error": "...", "details": ["..."] }`。
